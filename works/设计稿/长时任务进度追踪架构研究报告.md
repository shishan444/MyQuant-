## 1. 停滞任务恢复 (Stale Task Recovery)

### 1.1 社区通用解法

停滞任务（任务崩溃后仍停留在 "running" 状态）是所有任务队列系统的经典问题。社区通常采用以下策略组合：

- **心跳机制 (Heartbeat)**：工作线程定期更新时间戳，守护进程扫描超时的任务并标记为失败
- **确认延迟 (Ack Late)**：任务仅在完成后才从队列中移除，而非领取时；崩溃后任务可被重新分配
- **可见性超时 (Visibility Timeout)**：消息队列中，如果任务在指定时间内未被确认，自动变为可重新领取
- **启动时清理**：服务启动时扫描所有 "running" 状态的任务，将其重置为 "pending" 或标记为 "crashed"

### 1.2 成熟项目模式

#### Celery

Celery 提供了多层防护：

**确认机制**：
- `acks_late=True` -- 任务仅在执行完毕后才确认，而非被 worker 领取时。若 worker 在执行中崩溃，任务会重新回到队列
- `task_reject_on_worker_lost=True` -- 当 worker 进程异常终止（SIGKILL、OOM），任务被拒绝而非重新入队，防止无限重试

**超时控制**：
- `soft_time_limit` -- 到达时抛出 `SoftTimeLimitExceeded` 异常，允许任务优雅清理后退出
- `time_limit` -- 硬超时，到达时直接终止 worker 进程（无法清理）
- 典型模式：
```python
@app.task(bind=True, acks_late=True, soft_time_limit=300, time_limit=360)
def long_running_task(self):
    try:
        return do_work()
    except SoftTimeLimitExceeded:
        cleanup_in_a_hurry()  # 有 60 秒窗口完成清理
```

**生命周期钩子**：
- `before_start` / `on_success` / `on_failure` / `on_retry` / `after_return`
- 在 `on_failure` 中可检测是否为 worker 崩溃导致，执行状态修正
- Celery 的结果后端 (result backend) 独立于消息代理，即使 worker 崩溃，状态记录可能已经写入

**结果后端状态机**：
```
PENDING -> STARTED -> SUCCESS | FAILURE | RETRY | REVOKED
                      +-- 自定义状态 (如 PROGRESS)
```
- `STARTED` 状态附带时间戳，可用于检测停滞任务

#### Temporal

Temporal 采用了完全不同的思路 -- 持久化事件历史 (Event History)：

**心跳与超时检测**：
- Activity 必须调用 `activity.heartbeat()` 来表明自己仍然存活
- `heartbeat_timeout` 配置心跳间隔，连续 N 次未收到心跳则判定 Activity 失败
- 心跳时可携带详情 (`heartbeat_details`)，用于崩溃后的断点续传

**状态重建**：
- "When a Worker crashes, the Workflow Task times out, and another available Worker picks up the Task. The new Worker replays the Event History to reconstruct state."
- 工作流的所有决策都记录为事件，新的 worker 通过重放事件历史完整恢复状态
- Activity 的心跳详情可被下一个 worker 读取，实现真正的断点续传

#### Dramatiq

Dramatiq 的方案相对轻量：

**TimeLimit 中间件**：
- 在独立线程中监控任务执行时间，超时后通过异步异常终止工作线程
- 任务可捕获 `TimeLimitExceeded` 异常进行清理
```python
@dramatiq.actor(time_limit=5000)
def time_limited_task():
    try:
        long_running_operation()
    except TimeLimitExceeded:
        cleanup()
        raise
```

**dramatiq-abort 扩展**：
- 提供外部取消能力：`abort(message.message_id)`
- 依赖 Redis 作为后端存储 abort 信号

### 1.3 适用于单进程 SQLite 系统的方案

对于当前架构（单进程、后台线程、SQLite），推荐分层方案：

**第一层：启动时清理**
```python
def recover_stale_tasks():
    """服务启动时，将所有 running 状态的任务标记为 crashed"""
    crash_threshold = datetime.utcnow() - timedelta(minutes=5)
    db.execute(
        "UPDATE tasks SET status = 'crashed', "
        "error_message = 'Service restarted while task was running' "
        "WHERE status = 'running' AND updated_at < ?",
        (crash_threshold,)
    )
```

**第二层：心跳更新**
```python
# 在任务执行线程中，每个子阶段完成后更新心跳
def update_heartbeat(task_id: str):
    db.execute(
        "UPDATE tasks SET heartbeat_at = ? WHERE id = ?",
        (datetime.utcnow(), task_id)
    )

# 后台守护协程，定期扫描超时任务
async def stale_task_watcher():
    while True:
        await asyncio.sleep(60)
        threshold = datetime.utcnow() - timedelta(minutes=10)
        db.execute(
            "UPDATE tasks SET status = 'crashed', "
            "error_message = 'Heartbeat timeout' "
            "WHERE status = 'running' AND heartbeat_at < ?",
            (threshold,)
        )
```

**第三层：优雅关闭钩子**
```python
import atexit
import signal

active_tasks: dict[str, threading.Event] = {}

def graceful_shutdown(signum, frame):
    for task_id, stop_event in active_tasks.items():
        stop_event.set()
    # 等待任务完成或超时
    time.sleep(5)
    # 强制标记仍在运行的任务
    for task_id in active_tasks:
        db.execute("UPDATE tasks SET status = 'stopped' WHERE id = ?", (task_id,))

signal.signal(signal.SIGTERM, graceful_shutdown)
signal.signal(signal.SIGINT, graceful_shutdown)
```

### 1.4 权衡分析

| 方案 | 优点 | 缺点 | 适用场景 |
|------|------|------|----------|
| 启动时清理 | 实现简单，零运行开销 | 仅在重启时生效 | 必选项，兜底方案 |
| 心跳 + 守护协程 | 实时检测，粒度可控 | 需要额外的定时任务 | 任务运行时间长（> 10 分钟） |
| 信号钩子 | 进程退出时主动清理 | 无法处理 SIGKILL / 断电 | 优雅部署场景 |
| Temporal 式事件历史 | 完整状态重建 | 实现复杂度高，需要事件存储 | 当前不推荐 |

**结论**：单进程系统不需要 Celery 的 acks_late 或 Temporal 的事件重放。启动时清理 + 心跳监控 + 信号钩子的组合即可覆盖所有停滞场景。心跳间隔建议 30-60 秒，超时阈值设为心跳间隔的 5-10 倍（即 2.5-10 分钟无心跳判定为停滞）。

## 2. 细粒度进度状态建模 (Fine-grained Progress States)

### 2.1 社区通用解法

从粗粒度状态 (pending/running/paused/stopped/completed) 迁移到细粒度子阶段，社区通常采用以下模式：

- **在 running 状态内部定义子阶段**：保持顶层状态机简单，用额外字段描述当前阶段
- **结构化进度信息**：JSON 字段存储当前阶段、百分比、已处理数量等
- **嵌套任务/子任务**：父任务包含多个子任务，每个子任务有独立状态
- **步骤化日志**：记录每个步骤的开始/结束时间，而非仅记录最终状态

### 2.2 成熟项目模式

#### Celery -- 自定义状态

Celery 允许在标准状态机基础上定义任意自定义状态：

```python
@app.task(bind=True)
def upload_files(self, filenames):
    for i, file in enumerate(filenames):
        process_file(file)
        self.update_state(
            state='PROGRESS',
            meta={'current': i + 1, 'total': len(filenames),
                  'filename': file}
        )
```

关键设计决策：
- 自定义状态不影响标准状态机转换 -- `PROGRESS` 不是一个终止状态
- `meta` 字段可存储任意结构化数据
- 前端轮询 `AsyncResult.state` 和 `AsyncResult.info` 获取进度
- 状态更新写入结果后端（Redis/数据库），有写入开销

#### MLflow -- 嵌套 Run 与步骤化追踪

MLflow 提供了两层进度抽象：

**嵌套 Run (Nested Runs)**：
```python
with mlflow.start_run(run_name="hyperparameter_sweep") as parent_run:
    for lr in [0.001, 0.01, 0.1]:
        for batch_size in [16, 32, 64]:
            with mlflow.start_run(nested=True, run_name=f"lr_{lr}_bs_{batch_size}") as child_run:
                mlflow.log_params({"learning_rate": lr, "batch_size": batch_size})
                model = train_model(lr, batch_size)
                score = evaluate_model(model)
                mlflow.log_metric("accuracy", score)
```

**步骤化指标 (Step Metrics)**：
```python
with mlflow.start_run():
    for epoch in range(num_epochs):
        train_loss = train_model()
        val_loss = validate_model()
        mlflow.log_metrics(
            {"train_loss": train_loss, "val_loss": val_loss},
            step=epoch
        )
```

MLflow 的关键模式：
- **Run 状态**：`RUNNING` / `FINISHED` / `FAILED` / `KILLED` / `SCHEDULED`
- **嵌套结构**：父 Run 包含多个子 Run，形成树状进度视图
- **步骤追踪**：`step` 参数提供时间维度的进度，无需自定义状态
- **参数/指标分离**：`log_param` 记录配置，`log_metric` 记录数值进度，`log_artifact` 记录输出文件

#### Temporal -- 活动 (Activity) 粒度

Temporal 在工作流层面提供天然的步骤化：
- Workflow 由多个 Activity 组成，每个 Activity 是一个独立步骤
- Workflow 状态 = 所有 Activity 状态的聚合
- 每个 Activity 有独立的超时、重试、心跳配置
- 前端可通过 Workflow Query 查询任意时刻的进度

### 2.3 适用于单进程 SQLite 系统的方案

针对进化任务，建议采用 **分层状态模型**：

**数据模型设计**：
```sql
-- 任务表：保持顶层状态机简单
CREATE TABLE tasks (
    id TEXT PRIMARY KEY,
    status TEXT NOT NULL DEFAULT 'pending',
        -- pending | running | paused | stopped | completed | crashed
    current_phase TEXT,
        -- idle | data_loading | indicator_computation | population_init |
        -- generation_running | result_saving
    progress_json TEXT,  -- 结构化进度信息
    heartbeat_at TEXT,
    created_at TEXT,
    updated_at TEXT
);

-- 进度快照表（可选）：记录每个子阶段的详细信息
CREATE TABLE task_phases (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    task_id TEXT NOT NULL REFERENCES tasks(id),
    phase_name TEXT NOT NULL,
    status TEXT NOT NULL DEFAULT 'pending',
        -- pending | running | completed | failed | skipped
    started_at TEXT,
    completed_at TEXT,
    detail_json TEXT,    -- 阶段特定数据
    FOREIGN KEY (task_id) REFERENCES tasks(id)
);
```

**进度信息结构**：
```python
@dataclass(frozen=True)
class TaskProgress:
    phase: str              # 当前阶段
    phase_index: int        # 当前阶段序号
    total_phases: int       # 总阶段数

    # 阶段特定数据（以 generation_running 为例）
    current_generation: int | None
    total_generations: int | None
    best_fitness: float | None
    population_size: int | None

    def to_json(self) -> str:
        return json.dumps(asdict(self), ensure_ascii=False)

    @classmethod
    def from_json(cls, data: str) -> 'TaskProgress':
        return cls(**json.loads(data))
```

**阶段定义与转换**：
```python
class TaskPhase(enum.Enum):
    IDLE = "idle"
    DATA_LOADING = "data_loading"
    INDICATOR_COMPUTATION = "indicator_computation"
    POPULATION_INIT = "population_init"
    GENERATION_RUNNING = "generation_running"
    RESULT_SAVING = "result_saving"

PHASE_SEQUENCE = [
    TaskPhase.DATA_LOADING,
    TaskPhase.INDICATOR_COMPUTATION,
    TaskPhase.POPULATION_INIT,
    TaskPhase.GENERATION_RUNNING,
    TaskPhase.RESULT_SAVING,
]

def advance_phase(task_id: str, next_phase: TaskPhase) -> None:
    """原子性地完成当前阶段并进入下一阶段"""
    now = datetime.utcnow().isoformat()
    with db_transaction():
        # 标记当前阶段完成
        db.execute(
            "UPDATE task_phases SET status = 'completed', completed_at = ? "
            "WHERE task_id = ? AND status = 'running'",
            (now, task_id)
        )
        # 启动下一阶段
        db.execute(
            "INSERT INTO task_phases (task_id, phase_name, status, started_at) "
            "VALUES (?, ?, 'running', ?)",
            (task_id, next_phase.value, now)
        )
        # 更新主任务表
        db.execute(
            "UPDATE tasks SET current_phase = ?, updated_at = ? WHERE id = ?",
            (next_phase.value, now, task_id)
        )
```

**进化循环内的细粒度更新**：
```python
def run_evolution(task_id: str, config: EvolutionConfig, stop: threading.Event):
    advance_phase(task_id, TaskPhase.DATA_LOADING)
    data = load_market_data(config)
    update_progress(task_id, TaskProgress(
        phase="data_loading", phase_index=0, total_phases=5,
        current_generation=None, total_generations=None,
        best_fitness=None, population_size=None
    ))

    advance_phase(task_id, TaskPhase.INDICATOR_COMPUTATION)
    indicators = compute_indicators(data, config)

    advance_phase(task_id, TaskPhase.POPULATION_INIT)
    population = init_population(config)
    update_progress(task_id, TaskProgress(
        phase="population_init", phase_index=2, total_phases=5,
        current_generation=0, total_generations=config.max_generations,
        best_fitness=None, population_size=len(population)
    ))

    advance_phase(task_id, TaskPhase.GENERATION_RUNNING)
    for gen in range(config.max_generations):
        if stop.is_set():
            return
        population = evolve_one_generation(population, config)
        best = best_individual(population)
        update_progress(task_id, TaskProgress(
            phase="generation_running", phase_index=3, total_phases=5,
            current_generation=gen + 1,
            total_generations=config.max_generations,
            best_fitness=best.fitness,
            population_size=len(population)
        ))
        update_heartbeat(task_id)

    advance_phase(task_id, TaskPhase.RESULT_SAVING)
    save_results(task_id, population)
```

### 2.4 权衡分析

| 模式 | 优点 | 缺点 | 适用场景 |
|------|------|------|----------|
| 扁平 + JSON 进度字段 | 实现简单，查询高效 | 难以查询历史阶段耗时 | 大多数场景足够 |
| 阶段明细表 | 可追溯每个阶段的耗时与详情 | 多一张表，更新操作增加 | 需要性能分析、审计 |
| 嵌套子任务 | 灵活，支持并行子任务 | 复杂度高，需要树状查询 | 复杂工作流 |
| MLflow 式 step metrics | 时间序列数据，适合绘图 | 需要 step 参数管理 | 监控/可视化场景 |

**结论**：推荐 "扁平状态 + JSON 进度字段 + 可选阶段明细表" 的组合。主任务表保持 5 个粗粒度状态不变，通过 `current_phase` 和 `progress_json` 字段提供细粒度信息。阶段明细表用于性能分析，初期可不实现。

## 3. 停止信号响应性 (Stop Signal Responsiveness)

### 3.1 社区通用解法

长时间运行任务的取消是一个涉及多个层面的协同问题。社区通常分为两类：

- **协作式取消 (Cooperative Cancellation)**：任务在合适的检查点主动检测取消信号并自行终止
- **强制终止 (Forced Termination)**：外部强制杀死任务线程/进程

几乎所有成熟项目都选择协作式取消，因为强制终止会导致资源泄漏和状态不一致。

### 3.2 成熟项目模式

#### Celery -- 软硬超时 + 撤销

Celery 提供三层取消机制：

**REVOKED 状态**：
- `app.control.revoke(task_id)` -- 发送撤销信号
- `terminate=True` -- 同时发送 SIGTERM 到 worker 进程
- Worker 在下次收到任务消息时检查 revoke 列表

**软硬超时**：
```python
@app.task(soft_time_limit=60, time_limit=120)
def mytask():
    try:
        do_work()
    except SoftTimeLimitExceeded:
        # 有 60 秒窗口进行清理
        cleanup()
```
- `soft_time_limit`：抛出异步异常，任务可捕获并清理
- `time_limit`：硬终止，不可捕获

**检查点模式**（Celery 隐式使用）：
- 任务仅在消息边界（任务领取/完成）检查撤销状态
- 长时间运行的单一任务内部不会自动检查

#### Temporal -- 取消作用域与 CancelledError

Temporal 提供最优雅的取消模型：

**Activity 级取消**：
```python
@activity.defn
async def cancellable_activity():
    try:
        while True:
            await asyncio.sleep(0.5)
            activity.heartbeat("details")
    except asyncio.CancelledError:
        print("Activity cancelled")
        raise
```

**关键特性**：
- 取消通过 `CancelledError` 异常传递，任务可捕获并执行清理
- `heartbeat()` 调用处也是取消信号的检查点 -- 心跳兼作取消检测
- Activity 的 `heartbeat_details` 可用于断点续传
- 取消作用域 (Cancellation Scope) 支持嵌套和超时

#### Dramatiq -- TimeLimit + Abort

```python
# 超时取消
@dramatiq.actor(time_limit=5000)
def task():
    try:
        long_operation()
    except TimeLimitExceeded:
        cleanup()

# 外部取消（需 dramatiq-abort 扩展）
from dramatiq_abort import abort
abort(message.message_id)
```

Dramatiq 的 abort 通过在 Redis 中写入 abort 信号，Worker 在处理消息时检查该信号。检查粒度取决于中间件实现，通常在消息处理前后检查。

### 3.3 适用于单进程 SQLite 系统的方案

**当前问题**：停止信号仅在代际之间检查，意味着一代进化需要完成后才能响应停止请求。

**推荐方案：多层检查点**

```python
import threading
import enum

class StopRequest(enum.Enum):
    NONE = "none"
    GRACEFUL = "graceful"    # 完成当前个体后停止
    IMMEDIATE = "immediate"  # 尽快停止，可能在代中途


class TaskController:
    """任务控制器 -- 在主线程中创建，传递给任务线程"""

    def __init__(self):
        self._stop_event = threading.Event()
        self._stop_level = StopRequest.NONE
        self._lock = threading.Lock()

    def request_stop(self, level: StopRequest = StopRequest.GRACEFUL) -> None:
        with self._lock:
            self._stop_level = level
        self._stop_event.set()

    @property
    def stop_requested(self) -> bool:
        return self._stop_event.is_set()

    @property
    def stop_level(self) -> StopRequest:
        with self._lock:
            return self._stop_level

    def check_stop(self, level: StopRequest = StopRequest.GRACEFUL) -> None:
        """在检查点调用，如果停止请求级别满足则抛出异常"""
        if self.stop_requested and self.stop_level.value >= level.value:
            raise TaskStopRequested(self.stop_level)


class TaskStopRequested(Exception):
    """任务被请求停止时抛出"""
    def __init__(self, level: StopRequest):
        self.level = level
        super().__init__(f"Task stop requested: {level.value}")
```

**在进化循环中嵌入检查点**：
```python
def run_evolution(task_id: str, config: EvolutionConfig,
                  controller: TaskController) -> None:
    # 阶段转换时检查
    advance_phase(task_id, TaskPhase.DATA_LOADING)
    data = load_market_data(config)
    controller.check_stop()  # 数据加载后检查

    advance_phase(task_id, TaskPhase.INDICATOR_COMPUTATION)
    indicators = compute_indicators(data, config)
    controller.check_stop()  # 指标计算后检查

    advance_phase(task_id, TaskPhase.POPULATION_INIT)
    population = init_population(config)
    controller.check_stop()

    advance_phase(task_id, TaskPhase.GENERATION_RUNNING)
    for gen in range(config.max_generations):
        controller.check_stop()  # 代际之间检查

        for idx, individual in enumerate(population):
            # 个体评估后检查（仅 graceful 级别以上）
            fitness = evaluate(individual, indicators)
            controller.check_stop(StopRequest.GRACEFUL)

            # 交叉/变异后检查（仅 immediate 级别以上）
            offspring = crossover_and_mutate(individual)
            controller.check_stop(StopRequest.IMMEDIATE)

        population = select(population)
        update_progress(task_id, ...)
        update_heartbeat(task_id)
```

**FastAPI 端点**：
```python
# 全局任务注册表
```

**异常处理与状态记录**：
```python
def _run_task_wrapper(task_id: str, config: EvolutionConfig):
    """任务线程入口，包装异常处理"""
    controller = TaskController()
    active_controllers[task_id] = controller
    try:
        run_evolution(task_id, config, controller)
        update_task_status(task_id, "completed")
    except TaskStopRequested as e:
        update_task_status(task_id, "stopped")
        log_info(f"Task {task_id} stopped: {e.level.value}")
    except Exception as e:
        update_task_status(task_id, "crashed")
        log_error(f"Task {task_id} crashed", exc_info=e)
    finally:
        active_controllers.pop(task_id, None)
        update_heartbeat(task_id)  # 确保最终状态已写入
```

### 3.4 权衡分析

| 检查点密度 | 响应延迟 | 实现成本 | 数据一致性风险 |
|-----------|---------|---------|--------------|
| 仅代际之间（当前） | 分钟级 | 零 | 最低 |
| 代际 + 个体评估后 | 秒级 | 低 | 低 |
| 每次迭代 | 毫秒级 | 中 | 中（可能中断数据写入） |
| 强制终止线程 | 即时 | 低 | 极高（状态不可预测） |

**结论**：推荐 "代际 + 个体评估后" 的检查点密度。使用两级停止请求（graceful / immediate）让用户选择停止粒度。`threading.Event` 作为信号传递机制，检查开销接近于零（仅一次原子变量读取）。关键原则：检查点放置在"数据一致"的位置，即当前进度已安全保存或可以安全丢弃的位置。

## 4. SQLite 并发访问 (SQLite Concurrency)

### 4.1 社区通用解法

SQLite 的并发模型是"多读单写"：同一时刻可以有多个读取者，但写入者是排他的。社区处理并发写入的主要策略：

- **WAL 模式 (Write-Ahead Logging)**：允许读写并发，是 SQLite 并发的核心优化
- **busy_timeout**：当遇到锁冲突时，等待而非立即报错
- **连接池**：复用连接，减少连接创建开销和锁竞争
- **批量写入**：将多个写操作合并为一个事务，减少锁竞争次数
- **单一写入队列**：所有写操作通过一个专用线程/连接执行

### 4.2 成熟项目模式

#### SQLite 原生 -- WAL 模式

**WAL 模式核心特性**（来自 SQLite 官方文档）：

- 读操作不阻塞写操作，写操作不阻塞读操作
- 仍然只允许一个写入者（排他锁）
- WAL 文件在达到 1000 页时自动 checkpoint（将 WAL 内容合并回主数据库文件）
- `PRAGMA journal_mode=WAL` 是持久配置，只需设置一次
- 所有涉及自动 checkpoint 的操作（读取、写入）都可能触发 checkpoint

**推荐的 PRAGMA 配置**：
```sql
PRAGMA journal_mode = WAL;        -- 启用 WAL 模式
PRAGMA synchronous = NORMAL;      -- 平衡安全性与性能（WAL 模式下足够安全）
PRAGMA busy_timeout = 5000;       -- 锁冲突时等待 5 秒
PRAGMA cache_size = -2000;        -- 2MB 缓存（可根据实际情况调整）
PRAGMA foreign_keys = ON;         -- 启用外键约束
```

**busy_timeout 的关键性**：
- `busy_timeout=0`（当前配置）意味着任何锁冲突都立即返回 `SQLITE_BUSY` 错误
- 这在后台线程写入 + API 线程读取/写入的场景下几乎必然出问题
- 推荐值：3000-10000 毫秒（3-10 秒）

#### SQLAlchemy -- SQLite 连接池

**SQLAlchemy 2.0 的变化**（重要）：

自 SQLAlchemy 2.0 起，文件型 SQLite 数据库默认使用 `QueuePool`（之前默认是 `NullPool`）。这意味着连接池现在是默认行为。

**连接池选择**：

| 池类型 | 特点 | 适用场景 |
|-------|------|---------|
| `QueuePool` (默认) | 固定大小连接池，复用连接 | 多线程 Web 服务 |
| `StaticPool` | 单一共享连接 | 内存数据库 + 多线程 |
| `NullPool` | 无池化，每次创建新连接 | 调试、极低并发 |
| `SingletonThreadPool` | 每线程一个连接 | 极少使用 |

**推荐的 SQLAlchemy + SQLite 配置**：
```python
from sqlalchemy import create_engine, event

engine = create_engine(
    "sqlite:///path/to/database.db",
    connect_args={
        "check_same_thread": False,  # 允许跨线程使用连接
    },
    pool_size=5,           # 连接池大小
    max_overflow=10,       # 最大溢出连接数
    pool_timeout=30,       # 获取连接超时（秒）
    pool_recycle=3600,     # 连接回收时间（秒）
)

@event.listens_for(engine, "connect")
def set_sqlite_pragmas(dbapi_connection, connection_record):
    cursor = dbapi_connection.cursor()
    cursor.execute("PRAGMA journal_mode=WAL")
    cursor.execute("PRAGMA synchronous=NORMAL")
    cursor.execute("PRAGMA busy_timeout=5000")
    cursor.execute("PRAGMA foreign_keys=ON")
    cursor.close()
```

**关键注意事项**：
- `check_same_thread=False` 是多线程访问 SQLite 的前提
- 每个 SQLAlchemy 连接会执行 PRAGMA 设置（通过 connect 事件钩子）
- WAL 模式的 PRAGMA 在每个连接上执行是安全的 -- 已设置为 WAL 的数据库会直接返回 "wal"

### 4.3 适用于单进程 SQLite 系统的方案

针对当前架构（FastAPI + 后台线程 + SQLite），推荐以下配置：

**方案 A：SQLAlchemy 连接池（推荐）**

```python
# database.py
from sqlalchemy import create_engine, event, text
from sqlalchemy.pool import QueuePool

def create_app_engine(db_path: str) -> Engine:
    engine = create_engine(
        f"sqlite:///{db_path}",
        connect_args={"check_same_thread": False},
        poolclass=QueuePool,
        pool_size=5,
        max_overflow=5,
        pool_timeout=30,
        pool_recycle=1800,
    )

    @event.listens_for(engine, "connect")
    def _set_pragmas(conn, record):
        cursor = conn.cursor()
        cursor.execute("PRAGMA journal_mode=WAL")
        cursor.execute("PRAGMA synchronous=NORMAL")
        cursor.execute("PRAGMA busy_timeout=5000")
        cursor.execute("PRAGMA foreign_keys=ON")
        cursor.close()

    return engine
```

**方案 B：写操作序列化（可选增强）**

如果写操作冲突频繁（多个后台任务同时更新进度），可引入写操作队列：

```python
import queue
import threading

class SQLiteWriter:
    """将所有写操作序列化到单一队列，避免 SQLITE_BUSY"""

    def __init__(self, engine):
        self._engine = engine
        self._queue = queue.Queue()
        self._thread = threading.Thread(
            target=self._writer_loop, daemon=True
        )
        self._thread.start()

    def _writer_loop(self):
        while True:
            fn, args, kwargs, result_future = self._queue.get()
            try:
                with self._engine.begin() as conn:
                    result = fn(conn, *args, **kwargs)
                result_future.set_result(result)
            except Exception as e:
                result_future.set_exception(e)

    def execute_write(self, fn, *args, **kwargs):
        """在线程安全的环境中执行写操作"""
        result_future = concurrent.futures.Future()
        self._queue.put((fn, args, kwargs, result_future))
        return result_future.result(timeout=10)
```

**方案 C：WAL Checkpoint 控制（可选）**

WAL 文件增长过快时，可在低峰期手动 checkpoint：

```python
def checkpoint_wal(engine):
    """在低峰期执行 WAL checkpoint"""
    with engine.connect() as conn:
        conn.execute(text("PRAGMA wal_checkpoint(TRUNCATE)"))
```

### 4.4 权衡分析

| 配置 | 读性能 | 写性能 | 数据安全 | 实现复杂度 |
|------|-------|-------|---------|-----------|
| 默认 (DELETE 模式 + busy_timeout=0) | 差（读写互斥） | 差（立即 SQLITE_BUSY） | 高 | 零 |
| WAL + busy_timeout=5000 | 好（读写并发） | 中（等待锁） | 高 | 低 |
| WAL + 写队列 | 好 | 好（序列化避免等待） | 高 | 中 |
| WAL + synchronous=OFF | 好 | 极好 | 低（崩溃可能丢数据） | 低 |

**结论**：

必须做的：
1. 启用 WAL 模式 (`PRAGMA journal_mode=WAL`)
2. 设置 busy_timeout (`PRAGMA busy_timeout=5000`)
3. 允许跨线程 (`check_same_thread=False`)

建议做的：
4. 使用 SQLAlchemy QueuePool（2.0 默认行为）
5. 设置 `synchronous=NORMAL`（WAL 模式下足够安全，性能优于 FULL）

可选做的：
6. 写操作队列化（仅在写冲突确实频繁时）
7. WAL checkpoint 控制（仅在 WAL 文件增长过快时）

绝对不要做的：
- `synchronous=OFF` -- 崩溃时数据库损坏风险
- `busy_timeout=0` -- 任何并发场景都会报错
- 不使用 WAL 模式 -- 读写完全互斥

## 5. 综合建议：单进程 SQLite 系统的整体方案

### 5.1 架构总览

```
FastAPI (主进程)
  |
  +-- API 线程池 (uvicorn workers)
  |     |-- GET  /tasks/{id}          -- 查询任务状态与进度
  |     |-- POST /tasks/{id}/stop     -- 请求停止任务
  |     |-- GET  /tasks/{id}/stream   -- SSE 实时进度推送
  |
  +-- 任务执行线程 (ThreadPoolExecutor)
  |     |-- TaskController (停止信号)
  |     |-- 心跳更新 (每 30-60 秒)
  |     |-- 进度更新 (每代完成 / 每阶段转换)
  |
  +-- 守护协程 (asyncio)
        |-- 停滞任务检测 (每 60 秒扫描)
        |-- WAL checkpoint (可选，每小时)
```

### 5.2 数据库 Schema 变更


### 5.3 实时进度推送（SSE 方案）

对于前端进度更新，推荐使用 Server-Sent Events (SSE) 而非 WebSocket，因为进度推送是单向的（服务端 -> 客户端）：

```python
from sse_starlette.sse import EventSourceResponse

@router.get("/tasks/{task_id}/stream")
async def stream_task_progress(task_id: str):
    async def event_generator():
        last_progress = None
        while True:
            task = get_task(task_id)
            if task is None:
                break

            current = task.progress_json
            if current != last_progress:
                yield {"event": "progress", "data": current}
                last_progress = current

            if task.status in ("completed", "stopped", "crashed"):
                yield {"event": "done", "data": json.dumps({"status": task.status})}
                break

            await asyncio.sleep(1)  # 1 秒轮询间隔

    return EventSourceResponse(event_generator())
```

### 5.4 实施优先级

| 优先级 | 项目 | 影响范围 | 工作量 |
|-------|------|---------|-------|
| P0 | SQLite 配置 (WAL + busy_timeout) | 消除并发错误 | 0.5 天 |
| P0 | 启动时清理停滞任务 | 消除幽灵任务 | 0.5 天 |
| P1 | TaskController + 两级停止信号 | 提升响应性 | 1 天 |
| P1 | 细粒度进度 (current_phase + progress_json) | 前端可展示详细进度 | 1 天 |
| P1 | 心跳 + 守护协程 | 运行时停滞检测 | 0.5 天 |
| P2 | SSE 实时进度推送 | 前端体验提升 | 1 天 |
| P2 | 信号钩子 (SIGTERM/SIGINT) | 优雅部署 | 0.5 天 |
| P3 | 阶段明细表 | 性能分析与审计 | 1 天 |
| P3 | 写操作队列化 | 高并发写入优化 | 1 天 |

### 5.5 关键设计原则总结

1. **状态机保持简单**：顶层 6 个状态（含 crashed），子阶段通过 `current_phase` 字段表达
2. **协作式取消**：使用 `threading.Event` + 检查点模式，绝不强制终止线程
3. **心跳是生命线**：心跳兼作停滞检测和取消检查的锚点
4. **WAL 是前提**：所有并发方案都建立在 WAL 模式基础上
5. **写操作合并**：进度更新不要太频繁（建议最短间隔 1 秒），减少 SQLite 写入压力
6. **优雅降级**：如果心跳/进度更新失败，任务不应中断，仅记录警告
