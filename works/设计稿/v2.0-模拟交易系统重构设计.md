# v2.0 模拟交易系统重构设计

## 1. 设计背景

### 1.1 当前版本问题 (v0.15-v0.17)

以下问题经过代码级验证确认（验证日期: 2026-05-05）：

| # | 问题 | 代码证据 | 严重度 |
|---|------|---------|--------|
| 1 | **执行价格是 close 不是 open** | `position.py:213` `price = bar_close`，`bar_open` 从未作为参数传入 `process_bar()`。所有开仓/平仓/加仓/减仓操作均以 close 价格执行 | 高 |
| 2 | **实时阶段不用 shift(1)，回放阶段用 shift(1)** | `runner.py:240-245` 回放显式调用 `.shift(1)`；`runner.py:298-318` 实时阶段直接用 `sig_new.entries.iloc[i]`，无 shift | 高 |
| 3 | **无利润检查，机械执行** | `position.py:255-256` exit 仅检查 `position is not None`；`position.py:262` entry 仅检查 `position is None`。无最小利润/最小持仓时间保护 | 高 |
| 4 | **无目标仓位概念** | `Position` 数据类仅有 side/entry_price/quantity/margin，无 target 字段。`runner.py` 和 `position.py` 中无任何 target position 追踪 | 中 |
| 5 | **形成中 Bar 未过滤** | `fetcher.py` 和 `updater.py` 均无过滤逻辑。Binance API 返回的最后一根 Bar 可能是尚未收盘的 forming candle，被当作完整 Bar 处理 | 高 |
| 6 | **回放阶段冗余** | `runner.py:227-234` 全量加载+全量计算指标，`runner.py:240-276` 回放所有 Bar。但回放用已知数据，不产生验证信息 | 中 |
| 7 | **指标热身不足时静默产生 NaN** | `indicators.py:364-371` try/except 吞掉异常，NaN 传入信号计算。最大 lookback 200 Bar (EMA/SMA)，但无显式 warmup 检查 | 中 |
| 8 | **单任务限制** | `runner.py:135` `_tick()` 有 active_task 时直接 return。`TradingRunner` 是单线程，一个任务阻塞时第二个任务无法启动 | 低 |

### 1.3 根本原因分析

三个根本原因导致了上述所有问题：

**根因 1: PM 被设计为"回测镜像"而非"账户模拟器"**

`process_bar()` 镜像回测引擎的 `order_func_nb`，继承了回测的简化假设（只用 close、信号直接执行、无目标仓位）。回测的简化在批量计算中可接受，但逐 Bar 实时模拟中不可接受。

**根因 2: 信号到执行之间没有"思考"层**

策略 DNA 产生的 entry/exit/add/reduce 信号直接传入 PM，没有根据账户状态（持仓时间、盈亏、仓位大小）进行理性判断的中间层。

**根因 3: Runner 围绕"追赶-实时"模型设计**

先回放历史对齐状态再进入实时的模型引入了 shift(1) 不一致、全量重算开销、resume 复杂度等问题。新设计只需实时交易，不需要追赶历史。

### 1.4 重新设计核心理念

```
旧理念: 模拟交易 = 实时版回测
新理念: 模拟交易 = 虚拟交易账户

旧流程: 策略信号 → 直接执行 (机械的)
新流程: 策略信号 → 理性判断 → 最优执行 (智能的)
```

模拟交易的本质是：**假设你用真钱运行这个策略，会发生什么。** 其核心价值是结果可信——如果模拟交易赚了钱，你有理由相信真钱也能赚差不多。

### 1.5 设计决策记录

以下决策经过充分讨论确认：

| 决策项 | 结论 | 理由 |
|--------|------|------|
| 系统定位 | 虚拟交易账户 | 用户只需看"赚了还是亏了"，不需要理解执行细节 |
| 回放阶段 | 删除 | 只做实时交易，回放历史是回测的事 |
| 执行价格 | 下一Bar的open | 真实交易中信号产生后无法立即成交 |
| 信号-执行延迟 | 1Bar | pending_decision 机制，信号在Bar N产生，Bar N+1的open执行 |
| 判定引擎 | 必须有 | 避免无利润的机械交易 |
| 分批挂单 | V2加入 | 参考 Hummingbot DCA Executor 模式 |
| 自适应预测 | V3加入 | ATR + 动态倍数，根据历史覆盖率自动调整 |
| 外部依赖 | 不引入 | V1-V2 用已有的ATR + 纯Python，V3 可选引入 `arch` |

## 2. 架构设计

### 2.1 四层分离架构

```
┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐
│ 策略引擎  │ → │ 判定引擎  │ → │ 执行引擎  │ → │ 虚拟账户  │
│          │   │          │   │          │   │          │
│ "买"     │   │ "买3%,   │   │ "分3笔   │   │ 成交记录  │
│          │   │  先试探"  │   │  限价挂单"│   │ 持仓状态  │
│          │   │          │   │          │   │ 余额管理  │
│ 纯信号   │   │ 带上下文  │   │ 带预测   │   │ 最终状态  │
└──────────┘   └──────────┘   └──────────┘   └──────────┘
   策略DNA        判定规则        执行参数        账户状态
   (已有)        (新增)        (V2新增)        (重构)
```

每层职责：

| 层 | 职责 | 输入 | 输出 |
|----|------|------|------|
| 策略引擎 | 计算指标，生成交易信号 | DNA + OHLCV数据 | SignalSet (entry/exit/add/reduce) |
| 判定引擎 | 结合账户状态，判断是否/如何执行 | SignalSet + AccountState | Decision (action + target_pct) |
| 执行引擎 | 将决策转化为最优的订单计划 | Decision + PriceRange | OrderPlan (限价单列表) |
| 虚拟账户 | 管理余额、持仓、风控、记录 | OrderPlan + Bar数据 | 账户状态更新 + 交易记录 |

### 2.2 单Bar处理流程

```
Bar N 收盘，系统收到新数据
│
├── Step 0: 形成中 Bar 过滤 (数据入口)
│   └── 检查最后一根 Bar 是否为收盘状态
│       → Bar.time + interval > now? → 是形成中Bar，跳过
│       → 使用倒数第二根 Bar 作为当前 Bar
│       (防止基于不完整数据做交易决策)
│
├── Step 1: 风控检查 (最高优先级)
│   ├── SL/TP: 用 Bar N 的 high/low 检查
│   └── 清算检查 (leverage > 1 时)
│
├── Step 2: 执行上一Bar的决策
│   │
│   │ V1: pending_decision 存在?
│   │   → 是: 用 Bar N 的 open 价格执行
│   │   → 否: 跳过
│   │
│   │ V2: pending_orders 存在?
│   │   → 是: 用 Bar N 的 high/low 判定限价单成交
│   │   → 否: 跳过
│   │
│   └── 更新账户状态
│
├── Step 3: 信号评估
│   ├── 增量更新指标 (compute_all_indicators)
│   ├── 生成信号 (dna_to_signal_set)
│   └── 输出: SignalSet
│
├── Step 4: 判定引擎
│   ├── 输入: SignalSet + AccountState
│   ├── 应用判定规则 (见 §3.2)
│   └── 输出: Decision
│
├── Step 5: 执行引擎
│   │
│   │ V1: Decision != hold?
│   │   → 存为 pending_decision (等 Bar N+1 的 open 执行)
│   │
│   │ V2: Decision != hold?
│   │   → 预测 Bar N+1 价格范围
│   │   → 生成分批限价单
│   │   → 存为 pending_orders
│   │
│   └── 更新预测模型 (V2+: 用实际 high/low 反馈)
│
└── Step 6: 保存 + 推送
    ├── 资金费率扣除
    ├── 权益快照
    ├── 持久化到DB
    └── WebSocket 推送
```

### 2.3 V1 时序图：一次完整的交易周期

```
时间      Bar     系统行为
────────  ──────  ──────────────────────────────────────────
T+0:00    100     Bar 100 收盘
```

### 3.2 判定引擎 (core/trading/judgment.py)

#### 配置参数

```python
@dataclass
class JudgmentConfig:
    min_hold_bars: int = 3         # 最短持仓Bar数 (避免刚买就卖)
    min_profit_ratio: float = 2.0  # 平仓最低利润/手续费 比率
    initial_entry_pct: float = 0.33  # 首次开仓占目标仓位的比例
    profit_add_only: bool = True   # 仅在盈利时加仓
```

#### 判定规则优先级

```
输入: SignalSet + AccountState
输出: Decision

规则执行顺序 (高优先级先判断):

┌────────────────────────────────────────────────────────────┐
│ 规则 1: exit/reduce 信号 + 有持仓                          │
│                                                            │
│   if 持仓Bar数 < min_hold_bars:                            │
│     → HOLD (持仓时间不够，不卖)                              │
│                                                            │
│   if 未实现盈亏 < 手续费 * min_profit_ratio:                │
│     → HOLD (利润不够覆盖交易成本)                            │
│                                                            │
│   else:                                                    │
│     → CLOSE / REDUCE (正常平仓/减仓)                        │
└────────────────────────────────────────────────────────────┘

┌────────────────────────────────────────────────────────────┐
│ 规则 2: entry 信号 + 无持仓                                 │
│                                                            │
│   → OPEN                                                   │
│   target = DNA.position_size * initial_entry_pct           │
│   例: DNA说30%仓位 * 33%试探 = 先开10%                     │
└────────────────────────────────────────────────────────────┘

┌────────────────────────────────────────────────────────────┐
│ 规则 3: entry 信号 + 有同方向持仓                            │
│                                                            │
│   if 亏损中 AND profit_add_only:                            │
│     → HOLD (不逆势加仓)                                     │
│                                                            │
│   if actual_pct < target_pct:                               │
│     → ADD (补齐到目标仓位)                                   │
│                                                            │
│   if actual_pct >= target_pct:                              │
│     → HOLD (已满仓)                                         │
└────────────────────────────────────────────────────────────┘

┌────────────────────────────────────────────────────────────┐
│ 规则 4: entry 信号 + 有反方向持仓                            │
│                                                            │
│   → CLOSE (先平仓)                                         │
│   不在同一Bar反向开仓 (避免滑点叠加)                         │
│   下一Bar如果信号仍在 → 走规则2开新仓                        │
└────────────────────────────────────────────────────────────┘

┌────────────────────────────────────────────────────────────┐
│ 规则 5: 无信号                                              │
│                                                            │
│   if 有持仓 AND actual_pct < target_pct AND 盈利中:        │
│     → ADD (继续补齐仓位)                                    │
│                                                            │
│   else:                                                    │
│     → HOLD                                                 │
└────────────────────────────────────────────────────────────┘

注意: SL/TP 和清算不经过判定引擎，直接在 VirtualAccount 层执行。
      风控是硬性规则，不受判定逻辑影响。
```

### 3.4 执行引擎 (core/trading/execution.py) — V2

参考 Hummingbot DCA Executor 模式：

```python

class LimitOrder:

    quantity: float      # 数量
    limit_price: float   # 限价

    filled_price: float = 0.0
    filled_bar: str = ""

@dataclass
class OrderPlan:
    orders: list[LimitOrder]
    target_position_pct: float

@dataclass
```

### 3.6 重构后的 Runner (core/trading/runner.py)

```python
class TradingRunner(threading.Thread):
    """
    重构要点:
    - 删除回放阶段 (_execute_task 中的 for i in range(start_idx, len(df)))
    - 删除 shift(1) 逻辑
    - 删除 checkpoint 机制
    - 增加 pending_decision 机制
    - 使用 VirtualAccount 替代 PositionManager
    - 使用 JudgmentEngine 做信号判断
    """

    def __init__(self, db_path, data_dir, poll_interval=2.0):
        super().__init__(daemon=True, name="trading-runner")
        self.db_path = db_path
        self.data_dir = data_dir
        self.poll_interval = poll_interval
        self._stop_event = threading.Event()
        self._active_task_id: str | None = None

    def _execute_task(self, task_row, task_id, controller):
        """核心执行逻辑 (大幅简化)"""
        # 1. 标记 running
        self._update_status(task_id, "running", started_at=_now_iso())

        # 2. 解析DNA，创建组件
        dna = StrategyDNA.from_json(task_row["dna_json"])
        account = VirtualAccount(dna, init_cash=task_row["initial_cash"],
                                  fee=task_row["fee"])
        judgment = JudgmentEngine(JudgmentConfig())

        # V2:
        # execution = ExecutionEngine(ExecutionConfig())
        # predictor = PricePredictor(PredictionConfig())

        # 3. 恢复账户状态 (如果 resume)
        self._restore_account(account, task_row)

        # 4. 加载指标预热数据 (不执行交易)
        df = self._load_warmup_data(task_row["symbol"], task_row["timeframe"])
        if df is None or df.empty:
            self._update_status(task_id, "stopped", "no_data")
            return

        # 5. 实时主循环
        pending_decision = None  # V2: pending_orders = None
        bar_interval = _BAR_SECONDS.get(task_row["timeframe"], 14400)
        poll_wait = min(bar_interval, 60)

        while not controller.stop_requested:
            controller.check_stop()

            # 获取新数据
            new_df = self._fetch_and_update(task_row["symbol"], task_row["timeframe"])
            if new_df is not None and len(new_df) > len(df):
                new_df = compute_all_indicators(new_df)

                # Step 0: 过滤形成中 Bar
                new_df = self._filter_forming_bar(new_df, task_row["timeframe"])
                if len(new_df) <= len(df):
                    continue  # 没有新完成的 Bar

                df = new_df
                bar = df.iloc[-1]  # 最新完成的Bar

                # Step 1: 风控
                events = account.check_sl_tp(float(bar["high"]), float(bar["low"]))
                liquidation = account.check_liquidation(float(bar["close"]))
                if liquidation:
                    events.append(liquidation)

                # Step 2: 执行上一Bar的决策
                if pending_decision and not account.position:
                    # 如果上一步是平仓导致的，不要执行
                    pass
                elif pending_decision:
                    fills = account.execute_decision(
                        pending_decision, float(bar["open"])
                    )
                    events.extend(fills)
                    pending_decision = None

                # Step 3: 信号评估
                sig_set = dna_to_signal_set(dna, df)

                # Step 4: 判定
                state = account.get_state(float(bar["close"]))
                decision = judgment.evaluate(sig_set, state)

                # Step 5: 存储决策
                if decision.action != "hold":
                    pending_decision = decision

                # Step 6: 保存 + 推送
                account.apply_funding(float(bar["close"]))
                account.take_snapshot(df.index[-1].isoformat(), float(bar["close"]))
                self._log_events(task_id, events)
                self._save_account(account, task_id)
                self._push_update(account, task_id)

            controller._stop_event.wait(poll_wait)

    def _load_warmup_data(self, symbol, timeframe):
        """
        加载指标预热数据:
        - 加载最近 N 根 Bar (N = 指标所需的最大回看窗口)
        - 计算所有指标
        - 不执行任何交易
        - 验证指标热身: 检查最后 Bar 的信号列无 NaN
          (NaN 表示数据不足，需等待更多数据)
        """
        from core.data.mtf_loader import load_and_prepare_df
        from core.data.storage import find_parquet
        path = find_parquet(self.data_dir, symbol, timeframe)
        if not path.exists():
            return None
        df = load_and_prepare_df(path)
        return df

    def _filter_forming_bar(self, df, timeframe: str):
        """
        过滤形成中 Bar (未收盘的最后一根):
        - 获取当前 UTC 时间
        - 计算 Bar 的预期收盘时间: bar_time + interval
        - 如果最后一根 Bar 的收盘时间 > now → 是 forming candle
        - 返回去掉最后一根 Bar 的 df (如果需要)

        形成中 Bar 的价格是不完整的 (high/low/close 都在变化)，
        基于它做交易决策会导致错误信号。
        """
        import pandas as pd
        interval_seconds = _BAR_SECONDS.get(timeframe, 14400)
        now = pd.Timestamp.now(tz="UTC")
        last_bar_time = df.index[-1]
        if last_bar_time.tz is None:
            last_bar_time = last_bar_time.tz_localize("UTC")
        if last_bar_time + pd.Timedelta(seconds=interval_seconds) > now:
            return df.iloc[:-1]  # 排除形成中 Bar
        return df
```

## 9. 风险和注意事项

1. **runner.py 重写风险**: runner 是核心编排器，重写时需保持 WS 推送、状态持久化、任务管理的稳定性。建议渐进式重构，新逻辑在新方法中实现，逐步替换旧方法
2. **PositionManager 兼容性**: 现有测试基于 PM 的 `process_bar()` 接口，重构后需要重写测试。建议先写 account.py 的新测试，再逐步迁移
3. **前端适配**: V1 的执行模型变化（开盘价而非收盘价）可能导致前端展示的入场价格与之前不同。需要在前端更新展示逻辑
4. **预测模型冷启动**: PricePredictor (V2) 在前20-30根Bar没有足够的历史数据来评估覆盖率。初始阶段使用默认倍数，不调整
5. **判定规则可调性**: 判定规则的参数 (min_hold_bars, min_profit_ratio) 应该存储在任务配置中，而不是硬编码。后续可以做到前端可调
6. **指标热身 NaN 风险**: `indicators.py` 的 try/except 会静默吞掉计算异常，NaN 传入信号会导致错误决策。V1 启动时需验证预热数据的最后 Bar 无 NaN 信号，如果存在 NaN 则等待更多数据或拒绝启动。代码证据: `indicators.py:364-371`
7. **SL/TP 执行价格一致性**: 回测引擎 (engine.py) 的 `order_func_nb` 同样使用 close 作为 SL/TP 执行价格，当前系统与此一致。V1 沿用此简化：SL/TP 用 high/low 判断是否触发，但执行价格用 bar_open (非触发价)。这是模拟交易的保守简化——真实交易所会在触发价精确成交
