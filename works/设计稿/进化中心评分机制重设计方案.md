> 本文档记录基于工程验证的设计讨论，作为后续实施的上下文参考。
> 历史方案见：`评分系统重构需求.md`（基于旧设计的渐进修复方案，已被本文档替代）。

---

## 一、设计背景与目标

### 设计目标

系统的原始设计理念：**个人量化交易系统，用户不知道如何创建策略，通过自动探索找到策略，策略实验室视觉验证，模拟交易真实性验证。**

核心诉求：**让策略去运行获取收益。**

### 当前系统的问题

#### 问题 1：评分机制是"相对排名"而非"绝对质量判定"

当前 `score_strategy()` 输出 0-100 分，用于种群内相对比较。系统不回答"这个策略值不值得运行"，只回答"哪个策略比其他策略好"。

工程证据：
- `engine.py:240`：初始 champion_score = -1.0，任何正分数策略都能成为冠军
- `champion.py:45`：ChampionTracker 仅要求 score > 0
- 一个总收益为负的策略（-5%），只要 Sharpe 高、回撤小，可以得分 66.5 成为冠军
- 胜率不参与评分（三个模板的权重中都不包含 win_rate）

#### 问题 2：评分维度与目标不对齐

当前三套评分模板（explorer/optimizer/max_return）使用加权求和：
- 权重硬编码在 `templates.py` 中，用户无法调整
- 归一化函数给亏损策略基础分（annual_return=0 时有 10 分，`normalizer.py:11-19`）
- 只有 optimizer 模板有硬约束，explorer 和 max_return 完全允许负收益策略

#### 问题 3：进化产出无质量门控

策略从进化产出后、进入策略实验室或模拟交易之前，没有硬性门槛检查：
- `trading.py:73-102`：模拟交易启动时完全不检查策略质量，只校验 JSON 格式
- WS 推送所有 champion，不区分是否达标
- 用户可以拿任意策略（包括得分为 0 的）启动模拟交易

## 二、新设计方案：要求驱动评估

### 核心思想

**用用户输入的要求（收益率、回撤、胜率等）同时服务两个角色：**
1. 计算 fitness（连续梯度信号，引导进化搜索方向）
2. 判定资格（硬性门槛，决定策略能否展示和运行）

### 用户输入

进化任务创建时，用户配置"运行要求"（有默认值，不配置不让运行）：

| 要求维度 | 建议默认值 | 说明 |
|----------|-----------|------|
| min_annual_return | 15% | 最低年化收益 |
| max_drawdown | 30% | 最大允许回撤 |
| min_win_rate | 40% | 最低胜率 |
| min_total_trades | 10 | 最少交易次数（避免过拟合） |
| min_profit_factor | 1.2 | 最低盈亏比 |

### Fitness 计算

对每个要求维度计算"满足度"（0 到 1+），用乘积得出 fitness：

```
return_ratio = actual_return / required_return           # >1 表示超额达标
drawdown_ratio = required_drawdown / actual_drawdown     # >1 表示安全余量
winrate_ratio = actual_winrate / required_winrate        # >1 表示超额达标
trades_ratio = actual_trades / required_trades           # >1 表示充足
pf_ratio = actual_profit_factor / required_profit_factor # >1 表示超额达标

fitness = return_ratio * drawdown_ratio * winrate_ratio * trades_ratio * pf_ratio
```

**用乘积而非加权求和的原因：**
- 乘积惩罚短板——一个年化 100% 但回撤 60% 的策略，drawdown_ratio = 0.5，fitness 直接砍半
- 加权求和允许用一维优势补偿另一维劣势（年化 100% 可以抵消回撤 60%），不符合"每个要求都必须达标"的诉求
- 乘积保证 fitness >= 1.0 意味着所有维度都达标

**边界处理：**
- 某维度为 0 或负值（如收益为负）：对应 ratio = 0，fitness = 0
- fitness 无上界：超额达标越多 fitness 越高，进化有动力继续优化
- fitness = 1.0 表示刚好全部达标

### 资格判定

```
qualified = all([
    actual_return >= required_return,
    actual_drawdown <= required_drawdown,
    actual_winrate >= required_winrate,
    actual_trades >= required_trades,
    actual_profit_factor >= required_profit_factor,
])
```

fitness >= 1.0 一定 qualified，但 qualified 不意味着 fitness 高（可能刚达标）。

## 三、新链路全景

```
用户创建进化任务
  输入：symbol, timeframe, generations, population_size...
  输入：requirements = {
    min_annual_return: 15%,    ← 必填，有默认值
    max_drawdown: 30%,         ← 必填，有默认值
    min_win_rate: 40%,         ← 必填，有默认值
    min_total_trades: 10,      ← 必填，有默认值
    min_profit_factor: 1.2,    ← 必填，有默认值
  }
  （不配置 requirements 不让运行）
       |
       v
  EvolutionEngine.evolve(requirements=requirements)
       |
       +-- 每一代：
       |     1. batch_run() → metrics（不变）
       |        批量回测产出：annual_return, max_drawdown, win_rate,
       |                     total_trades, profit_factor, sharpe_ratio...
       |
       |     2. compute_fitness(metrics, requirements) → fitness + qualified
       |        替代原来的 score_strategy()
       |
       |     3. 按 fitness 排序种群（与当前按 score 排序逻辑相同）
       |
       |     4. fitness 消费（进化引擎内部，不变）：
       |        - 锦标赛选择父本（fitness 高的更容易被选中）
       |        - 精英保留（top N 直接存活）
       |        - 自适应突变 record(fitness)
       |        - 早停检查（fitness >= 1.0 可作为达标信号）
       |        - 冠军追踪（历史最高 fitness）
       |        - stagnation 驱动突变权重变化
       |
       |     5. 交叉 + 变异 → 下一代（不变）
       |
       v
  每代回调 runner.on_generation()
       |
       +-- qualified 消费（新增门控）：
       |     - qualified=True → 保存到 strategy 表、WS 推送给前端
       |     - qualified=False → 不展示、不保存
       |     - champion 必须同时 qualified 才能成为冠军
       |
       +-- fitness 消费（与当前 score 消费一致）：
       |     - save_history(best_fitness, avg_fitness)
       |     - save_snapshot(best_fitness)
       |     - 自适应突变、停滞检测
       |
       v
  进化完成
       ├── 有 qualified 策略 → 前端展示"达标策略"，按 fitness 排序
       ├── 无 qualified 策略 → 前端展示"未找到达标策略"，展示最接近要求的策略供参考
       |
       v
  策略实验室（视觉验证）
       └── 只有 qualified 策略可进入
       |
       v
  模拟交易（真实性验证）
       └── 只有 qualified 策略可运行（资格门控）
```

## 五、关键设计决策与理由

### 决策 1：用乘积而非加权求和

**理由：** 用户的诉求是"每个要求都必须达标"，不是"某个维度特别好可以补偿另一个维度的不足"。乘积天然惩罚短板，与这个诉求对齐。

### 决策 2：fitness 无上界（不像当前 score 封顶 100）

**理由：** 当前 score 封顶 100 导致进化在接近满分时梯度消失（99.5 和 100 之间几乎没有差异）。无上界的 fitness 让进化始终有动力继续优化。fitness = 1.5（所有维度超额 50%）比 fitness = 1.0（刚好达标）好，进化会追求前者。

### 决策 3：保留 metrics.py 中的全维度指标计算

**理由：** 用户可能需要查看 Sharpe、Sortino、Alpha 等指标做判断，这些指标在策略实验室和模拟交易中有展示价值。只是它们不参与 fitness 计算。

### 决策 4：不保留旧的评分模板系统

**理由：** 三套模板（explorer/optimizer/max_return）的差异化是权重比例不同，本质上还是同一套机制。用 requirements 替代后，用户通过调整门槛值实现同样的差异化，且更直观——"我要至少 15% 收益"比"选择 optimizer 模板"更易懂。

## 六、待讨论的开放问题

### 问题 1：默认值的具体数值

建议的默认门槛（15% 年化、30% 回撤、40% 胜率、10 次交易、1.2 盈亏比）是否合理？需要结合历史回测数据验证这些门槛的通过率——如果太高（95% 策略不达标），进化搜索效率会很低；如果太低（所有策略都达标），门控形同虚设。

### 问题 2：early_stop 的 target 调整

当前 `engine.py:59` 的 `if current_best >= self.target_score`（target 默认 100）需要调整。新方案中 target 应该是 1.0（所有要求刚好达标），或者不设 target 让进化跑到代数上限。

### 问题 3：无达标策略时的用户体验

进化 200 代后仍然没有 qualified 策略的情况如何处理？建议：
- 展示"最接近要求"的策略，附带各维度的差距
- 允许用户调整 requirements 后重新进化
- 前端展示各维度的达标率趋势（如"收益达标率 30%，回撤达标率 80%"）

### 问题 4：_TEMPLATE_MUTATION_BIAS 的替代方案

当前基于模板名调整突变权重（explorer 偏向指标替换，optimizer 偏向参数微调）。新方案中应该基于什么调整？建议基于 requirements 的满足情况：如果收益维度长期不达标，增加指标替换力度；如果只是参数微调的优化空间，增加参数变异力度。

## 七、相关工程事实（已验证）

### 7.1 策略层数据源（已超越 OHLCV）

策略层已存在完整的衍生数据管线（OI + Funding Rate），不是纯 OHLCV：
- `derivatives_fetcher.py`：独立获取 OI 和 Funding Rate
- `derivatives_merger.py`：ffill 合并到 OHLCV DataFrame
- `mtf_loader.py:124-151`：自动检测并合并，优雅降级
- `indicators.py:279-312`：5 个衍生数据指标
- `registry.py:370-399`：已注册，可被进化搜索

### 7.2 回测与模拟交易的定位差异（设计确认）

两者服务于不同阶段，设计差异是正确的：
- **回测引擎**：vectorbt Numba JIT，批量处理，服务于进化搜索的"快"
- **模拟交易**：纯 Python 流式处理，JudgmentConfig 规则引擎，限价单，服务于策略验证的"真"
- 共享 `dna_to_signal_set()` 信号生成层，信号之后路径完全不同
- ReplayRunner 是两者间的桥梁（用模拟交易逻辑跑历史数据）

### 7.3 进化引擎搜索空间现状

当前搜索空间已覆盖 10 个维度（10 种 SignalRole、14 种条件类型、37 个指标、MTF、方向决策、仓位管理、风险参数），但无显式 REGIME 基因。Fitness 评估只有全周期聚合指标，无分市场状态度量。

### 7.4 score 在进化引擎中的消费点

score（将来是 fitness）在进化引擎内被消费 7 次：排序、锦标赛选择、精英保留、自适应突变、早停检查、冠军追踪、停滞驱动。在 runner 层被消费 6 次：history、snapshot、tracker、DB、策略提取、WS。只要替换后的 fitness 仍是可比较大小的数值，这 13 个消费点不需要修改逻辑。
