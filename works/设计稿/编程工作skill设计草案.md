# 编程工作 Skill 设计草案

> 日期: 2026-05-14
> 状态: 草案（第三轮，架构确认完毕）
> 目的: 替代现有 feature-dev skill，构建统一的编程工作入口

---

## 一、设计目标

一个 skill 作为所有编程类工作的统一入口，按固定流程完成从分析到实现到验证的全过程。

替代对象：`plugin:feature-dev:feature-dev`（7 阶段线性管道，流程过重、缺少验证和 TDD）

---

## 二、执行模型

```
┌─────────────────────────────────────────────────┐
│  SKILL.md（唯一的流程控制者）                       │
│                                                  │
│  拥有：完整上下文、全局决策权、用户交互             │
│                                                  │
│  阶段 A → 加载 reference 按需指导                  │
│         → 创建 Agent 探索代码、验证假设             │
│         → 自己构建推理链、做决策                    │
│                                                  │
│  门控 → 呈现推理链，等用户确认                      │
│                                                  │
│  阶段 B → 加载 reference 按需指导                  │
│         → 自己写测试、写代码（TDD 循环）            │
│         → 创建 Agent 跑长测试                      │
│                                                  │
│  校验 → 自己对比推理链 vs 实际                      │
└─────────────────────────────────────────────────┘
```

三类资源：

| 资源 | 角色 | 何时使用 |
|------|------|---------|
| SKILL.md | 流程控制者、决策者、用户交互 | 始终 |
| reference 文件 | 阶段性知识指导 | 到达该阶段时按需加载 |
| Agent | 隔离的执行劳动力（探索、验证、长测试） | 需要并行或隔离时 |

## 三、流程结构：两个门控循环

### 3.1 整体结构

```
阶段 A（分析闭合循环）:
  理解意图 → 根因分析+方案设计 → 实际情况验证
       ↑                              ↓
       └──── 发现差距，深化理解 ←──────┘

  出口条件：推理链闭合

  ── 门控：用户确认推理链 ──

阶段 B（实现闭合循环）:
  评估规划实施 → TDD(Red) → 写代码(Green) → 测试验证
       ↑                                    ↓
       └──── 测试失败，回到实现 ←────────────┘

  出口条件：测试全绿

  ── 最终校验：推理链 vs 实际逐环对比 ──
```

### 3.2 流程原则

- **所有任务走同样的步骤**，不存在快速通道或跳步机制
- **变化的是深度，不是步骤**——"改一个变量名"和"重构状态管理"走同样的流程，每个步骤的深度差 60 倍
- **"这个任务很简单"是未经验证的假设**，假设必须被验证，不能成为跳过流程的理由

### 3.3 阶段 A 和阶段 B 的关系

- 阶段 A 不闭合就不进阶段 B——在错误前提上构建正确的方案，是最浪费的事情
- 两个循环之间有用户确认门控，防止分析不充分就直接实现
- 阶段 B 有权回退到阶段 A，但只回退到推理链断裂的具体环节，且必须通知用户

---

## 四、推理链：阶段 A 的核心产出

### 4.1 推理链结构

阶段 A 的产出不是"信息集合"，而是一条经过验证的推理链：

```
问题定义（什么坏了/缺什么）
    ↓ 因为
根因定位（为什么会这样）
    ↓ 所以
解决策略（怎么修/怎么建）
    ↓ 限于
范围边界（改什么、不改什么）
    ↓ 达到
验收标准（怎么判断修好了/建好了）
    ↓ 考虑到
风险披露（可能出什么问题）
    ↓ 按照
实施顺序（先做什么后做什么）
```

每一环依赖上一环。如果"根因定位"错了，后面所有环节都建立在错误基础上。阶段 A 的循环迭代就是在逐步构建和验证这条链。

### 4.2 推理链的 7 环不裁剪

所有任务必须产出完整的 7 环推理链。不存在可以省略某些环节的任务类型——深度可变，环节不减。

"改一个变量名"的推理链：问题=拼写错误 → 根因=输入失误 → 策略=重命名 → 范围=1 行 → 验收=编译通过+测试通过 → 风险=无 → 顺序=单步。每一环都在，各一句话。

### 4.3 验证步骤验证的是推理链，不是方案

验证步骤验证的不是"方案好不好"，而是"推理链的前几环是否成立"。实际案例（2026-05-13）：
- 假设 BUG-1 存在 → agent 去代码验证 → 确认精确行号
- 假设 _min_replay 是崩溃恢复 → agent 发现它主要是 pause/resume 触发 → 修正根因定位
- 假设 long/short 分支是死代码 → agent 确认字符级一致

## 五、门控：推理链冻结与用户确认

### 5.1 方案的本质

方案不是填写的表格，而是阶段 A 的**承诺点**：

- 阶段 A 是探索性的——收集信息、测试假设、修正理解，没有承诺
- 阶段 B 是承诺性的——基于特定理解去实现，改主意有代价
- **方案是两者之间的分界线**

用户确认的不是"这个方案看起来不错"，而是"这条推理链我认可，可以基于它去实现"。

### 5.2 方案的存在形式

利用 Claude Code 的 plan 文件机制：
- 阶段 A 开始时创建 plan
- 每次循环迭代更新 plan（活文档）
- 用户确认时，plan 冻结为实施基准
- 阶段 B 对照 plan 执行
- 最终对比用 plan 作为基准

## 六、Skill 架构

### 6.1 文件结构

```
skills/programming-work/
  SKILL.md                                # 流程框架 + 编排规则（~200 行）
  references/
    context-scanning.md                    # 启动阶段：如何扫描和继承项目上下文
    root-cause-analysis.md                 # 阶段 A：根因分析技术和收敛判断
    verification-guide.md                  # 阶段 A：如何设计验证、构造 agent prompt
    reasoning-chain-guide.md               # 阶段 A：推理链构建标准和常见缺陷
    gate-presentation.md                   # 门控：如何呈现推理链供用户确认
    tdd-guide.md                           # 阶段 B：TDD 执行方法和测试设计
    implementation-guide.md                # 阶段 B：增量实施和范围控制
    comparison-guide.md                    # 最终校验：推理链 vs 实际对比方法
```

### 6.2 reference 文件的定位

- 不是任务类型模板（不存在分类器）
- 是阶段性执行指导——到达该阶段时按需加载
- 每个 reference 回答：这个阶段怎么做才算做好？常见问题是什么？怎么判断可以进入下一阶段？

### 6.3 SKILL.md 的定位

- 流程框架（两个循环的结构和流转规则）
- 编排逻辑（何时加载哪个 reference、何时用 agent、何时问用户）
- 上下文扫描规则
- Agent 使用的基本原则
- 保持在 ~200 行，不包含具体执行指导

## 七、编排层 vs 执行层分工

### 7.1 Skill 做什么（编排层）

| 职责 | 原因 |
|------|------|
| 理解意图 | 需要和用户交互、澄清需求 |
| 根因分析 | 需要综合多源信息做判断 |
| 推理链构建 | 需要全局视野串联各环节 |
| 用户门控 | 需要等待用户确认 |
| TDD 循环 | 紧密的 Red-Green-Refactor 循环，不适合委派 |
| 决策和回退 | 跨阶段决策需要完整上下文 |
| 推理链 vs 实际对比 | 需要同时看到 plan 和代码 |

### 7.2 Agent 做什么（执行层）

| 职责 | 原因 |
|------|------|
| 代码探索 | 读大量文件追踪调用链，隔离探索不污染主上下文 |
| 假设验证 | 可并行验证多个假设 |
| 长测试执行 | 不阻塞主对话 |

### 7.3 Agent 使用策略

不预设 agent 类型。根据当前步骤的具体需求临时封装，每次构造专属 prompt。

Agent 的使用是可选的——缺少 agent 时 skill 可降级（自己执行探索步骤）。

## 八、上下文继承

skill 在"理解意图"阶段主动扫描项目上下文：

| 上下文源 | 位置 | 用途 |
|---------|------|------|
| CLAUDE.md | 项目根目录 | 项目级规则和约束 |
| works/设计稿/ | 工程目录 | 设计方案，理解系统意图 |
| works/bug/ | 工程目录 | Bug 文档，理解已知问题 |
| Memory 系统 | ~/.claude/projects/.../memory/ | 历史工作上下文 |
| git log | VCS | 近期变更，理解当前开发状态 |

不要求全部读取，但必须主动扫描目录结构和关键文件的标题/头部，判断哪些与当前任务相关。具体方法见 references/context-scanning.md。

## 九、TDD

不是笼统的"先写测试"，而是明确的 Red-Green-Refactor 循环：

```
1. Red:   写测试，定义"完成"的标准。运行，确认失败（证明测试有意义）
2. Green: 写最小代码让测试通过
3. Refactor: 如果需要，重构代码（测试保护下安全重构）
```

每个测试对应推理链"验收标准"中的一个条件。测试覆盖了所有验收标准 = TDD 完整。具体方法见 references/tdd-guide.md。

## 十、推理链 vs 实际对比

阶段 B 完成后，逐环验证推理链是否被执行：

| 推理链环节 | 对比什么 | 偏差处理 |
|-----------|---------|---------|
| 问题定义 | 实际解决的问题是否是原始定义的问题 | 偏差必须报告 |
| 根因定位 | 修复是否针对了真正的根因 | 偏差必须报告 |
| 解决策略 | 实际采用的策略是否和方案一致 | 偏差必须报告 |
| 范围边界 | 实际修改是否在范围内 | 超范围的改动逐条说明原因 |
| 验收标准 | 所有验收标准是否都被满足 | 未满足的标准说明原因和补救方案 |
| 风险 | 是否有未预见的风险出现 | 新风险说明影响和应对 |
| 实施顺序 | 是否按计划的顺序执行 | 跳过的步骤说明原因 |

偏差不都需要回退——有些是合理的实施调整。但偏差必须被显式识别，不能悄悄溜过去。用户决定是否接受。

具体方法见 references/comparison-guide.md。

## 十一、与 feature-dev 的关键差异

| 维度 | feature-dev | 本设计 |
|------|-------------|--------|
| 流程结构 | 7 阶段线性管道 | 两个门控循环 |
| 验证步骤 | 无 | 分析循环中强制验证 |
| TDD | 无（测试在审查阶段） | Red-Green-Refactor 循环 |
| 方案本质 | 无方案机制 | 推理链承诺点 |
| 任务处理 | 分类器 + 不同模板 | 统一流程，自然适应 |
| 流程弹性 | 所有任务同一深度 | 固定步骤，可变深度 |
| 上下文继承 | 从零开始 | 主动扫描项目上下文 |
| 最终对比 | 无 | 推理链 vs 实际逐环对比 |
| 执行模型 | 预设 agent 类型 | 一个 skill + 按需 agent |
| 子系统 | 无 | reference 按阶段加载 |
