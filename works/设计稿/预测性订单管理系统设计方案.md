> 版本: v1.0

> 状态: 讨论中

## 1. 背景与动机

### 1.1 当前系统的问题

当前模拟交易的决策流程是"信号驱动 + 即时执行"：

```
DNA信号评估 → judgment规则 → Decision(做/不做) → 下一bar市价执行
```

这种设计有两个根本缺陷：

1. **信号和预测是割裂的**。策略DNA说"RSI<30应该做多"（信号），PriceRangePredictor说"预测下根bar价格区间[94,98]"（预测）。这两个信息没有合并——信号独立决定"做不做"，预测只在开仓后才介入（管理加仓tranches）。预测能力被浪费了一半。

2. **没有订单生命周期管理**。系统只有"即时决策"(Decision)和"加仓挂单"(Tranche)，没有统一的"订单"概念。入场永远是市价，不存在"在好价格挂限价单等待成交"的逻辑。

### 1.2 目标

将模拟交易系统从"被动反应式信号执行"重构为"预测性订单管理系统"：

```
信号(定方向) + 预测(定价格) → 限价挂单 → 预测驱动管理(等待/调整/取消) → 成交/取消
```

核心验证命题：**预测性挂单系统的入场价格，是否系统性优于"看到信号就市价做"？**

### 1.3 约束

- 15m K线是分析和决策的最小周期
- 5m 是订单监控周期（不用于决策，仅检查SL/TP和订单成交）
- SL用触发价执行（stop-market），TP用限价执行
- 系统是方向性交易（单边入场），不是做市商（双边报价）

## 3. 理论基础

详见《限价单最优挂单价格研究.md》。本方案的定价公式基于以下学术研究：

### 3.1 核心原理

**原理1：成交概率与挂单距离的关系**

限价单的成交概率随距中间价距离呈指数衰减：

```
lambda(delta) = A * exp(-kappa * delta)
```

在GARCH预测框架下，可以用正态分布CDF近似：

```
P_fill_buy(p) = Phi((p - mu) / sigma)      // 买入限价在p的成交概率
P_fill_sell(p) = 1 - Phi((p - mu) / sigma)  // 卖出限价在p的成交概率
```

其中 Phi 是标准正态CDF，mu 和 sigma 来自GARCH预测。

**原理2：最优挂单距离与波动率成正比**

Guo-De Larrard-Ruan (2017) 解析最优解：

```
delta* = sigma * sqrt(tau / pi)
```

tau 是订单暴露时间，sigma 来自 GARCH。在我们的场景中 sigma 已经是 per-bar 的，简化为：

```
delta* = alpha * sigma
```

alpha 由信号置信度和风险偏好决定。

**原理3：逆向选择风险**

限价单成交不总是好事——远离中间价的成交往往意味着价格在朝不利方向移动（Lehalle-Mounjid 2017, DeLise 2024）。因此不应过度追求极端价格，需要用最低成交概率阈值来保护。

### 3.2 与学术模型的区别

| 特征 | 学术模型(A-S等) | 本系统 |
|------|----------------|--------|
| 交易类型 | 做市（双边报价） | 方向性（单边入场） |
| 时间尺度 | 毫秒~秒 | 15分钟 |
| 数据依赖 | 订单簿深度 | GARCH预测区间 |
| 目标 | 最大化价差收益 | 在好价格入场 |
| 库存管理 | 核心（做市商控制持仓） | 简化（方向性交易无需连续库存管理） |

结论：**借鉴学术原理（成交概率估算、价格-成交权衡），但不套用完整做市模型。**

### 4.3 订单价格计算

#### 定价公式

```
delta_base = alpha_factor * sigma

做多: order_price = mu - delta_base,  clamp(prediction.low, mu)
做空: order_price = mu + delta_base,  clamp(mu, prediction.high)

其中:
  mu = (prediction.low + prediction.high) / 2   // 预测中值
  sigma = prediction.width                        // GARCH半宽
  alpha_factor = f(confidence)                    // 由置信度调节

  alpha_factor = base + range * confidence
  - confidence = 0.1 → alpha = 0.35 (保守，靠近中间价)
  - confidence = 1.0 → alpha = 0.80 (激进，靠近预测边界)
```

#### confidence来源

MTF综合引擎已经计算了 confidence（`mtf_engine.py:599-619`）：

```python
confidence = confluence * 0.5 + momentum * 0.3 + abs(direction) * 0.2
# clip to [0.1, 1.0]
```

这意味着：
- 多时间周期共振度高 + 动量一致 → confidence高 → 挂更优价格（信号更可靠，可以等更好的入场价）
- 信号模糊、共振度低 → confidence低 → 挂接近中间价（信号不确定，优先确保成交）

#### 成交概率验证

```python
from scipy.stats import norm

if side == "long":
    p_fill = norm.cdf((price - mu) / sigma) if sigma > 0 else 0.5
else:
    p_fill = 1 - norm.cdf((price - mu) / sigma) if sigma > 0 else 0.5

if p_fill < min_fill_prob:
    # 成交概率太低，回退市价执行
    order_type = "market"
```

alpha_factor 的计算公式中的参数可以作为DNA的可进化基因：


### 4.4 订单有效性判断

```python
def is_order_still_valid(order: Order, new_prediction: PredictionResult,
                         new_signals: BarSignals) -> bool:
    """预测驱动的订单有效性判断。"""

    # 条件1：新预测区间是否仍覆盖挂单价格
    price_in_range = new_prediction.low <= order.price <= new_prediction.high

    # 条件2：信号方向是否一致（不要求信号再次触发，只要求不反向）
    no_reversal = not (new_signals.exit or new_signals.reduce)

    return price_in_range and no_reversal
```

**关键设计决策**：信号不需要每根bar都触发才保持订单有效。只要没有反向信号，且预测仍覆盖挂单价，就继续等待。这是"预测驱动"和"信号驱动"的本质区别。

#### 完整的管理决策表

| 新预测覆盖价格? | 信号方向一致? | 动作 |
|:---:|:---:|:---|
| YES | YES | KEEP — 继续等待 |
| YES | NO | CANCEL — 信号反转，取消订单 |
| NO | YES | ADJUST — 预测漂移，调整到新区间内（P1阶段） |
| NO | NO | CANCEL — 预测漂移 + 信号消失 |

```python
# runner.py 主循环改造

while not controller.stop_requested:
    # ... MTF数据刷新（不变）...
    # ... 获取新bar数据（不变）...

    for i in range(len(df), len(new_df)):

        events.extend(sl_tp_events)

        # Step 4: 评估信号

        state = account.get_state(float(row["close"]))

        # Step 5: 生成订单（新逻辑，替代 evaluate + pending_decision）
        if not state.has_position:
            # 无仓 → 检查入场信号
            if signals.entry:
                order = order_manager.generate_order(signals, prediction, state, config)
                if order:
                    order_manager.active_orders.append(order)
        else:
            # 有仓 → 评估出场/加仓信号
            decision = evaluate(signals, state, config)
            if decision.action in ("close", "reduce"):

                events.extend(account.execute_decision(decision, bar_open))
            elif decision.action == "add" and prediction:
                # 加仓 → 生成限价挂单
                order = order_manager.generate_order(signals, prediction, state, config, source="add")
                if order:
                    order_manager.active_orders.append(order)

        # Step 6: 资金费 + 快照（不变）
        account.apply_funding(bar_close)
        account.take_snapshot(bar_time, bar_close)
```

## 5. SL/TP执行价格修复

### 5.1 当前问题

`check_sl_tp()` (`account.py:262-285`) 使用 bar_open 作为 SL/TP 的执行价格，这不符合真实交易逻辑：

- SL 是 stop-market 订单：价格触及止损位时触发，执行价应该是**止损价本身**（或略差）
- TP 是 take-profit 订单：价格达到止盈位时触发，执行价应该是**止盈目标价**

### 5.2 修复方案

```python
def check_sl_tp(self, bar_high: float, bar_low: float) -> list:
    if self.position is None:
        return []
    events = []
    pos = self.position
    ep = pos.entry_price

    if pos.side == "long":
        sl_price = ep * (1.0 - self._stop_loss)
        tp_price = ep * (1.0 + self._take_profit) if self._take_profit else None

        if self._stop_loss > 0 and bar_low <= sl_price:
            # SL: stop-market, 执行价 = 止损价
            events.append(self._close_position(sl_price, "sl"))
        elif tp_price and tp_price > 0 and bar_high >= tp_price:
            # TP: limit, 执行价 = 止盈目标价
            events.append(self._close_position(tp_price, "tp"))
    else:  # short
        sl_price = ep * (1.0 + self._stop_loss)
        tp_price = ep * (1.0 - self._take_profit) if self._take_profit else None

        if self._stop_loss > 0 and bar_high >= sl_price:
            events.append(self._close_position(sl_price, "sl"))
        elif tp_price and tp_price > 0 and bar_low <= tp_price:
            events.append(self._close_position(tp_price, "tp"))

    return events
```

## 6. 实施规划

### 6.1 分阶段策略

#### P0: 核心概念验证

**目标**：验证"预测性挂单入场 vs 市价入场"的价格质量差异。

**改动范围**：

| 文件 | 改动内容 |
|------|---------|
| `core/trading/types.py` | 新增 Order 数据结构 |

| `core/trading/runner.py` | 主循环改造，接入 OrderManager |

**不改动**：

- 信号评估管线（`executor.py`、`mtf_engine.py`）
- 预测系统（`predictor.py`、`garch.py`、`factors.py`）
- 数据获取层

**验证方式**：
- 同一策略DNA，同一时间段
- 路径A（对照组）：信号 → 市价执行
- 路径B（实验组）：信号+预测 → 限价挂单 → 预测驱动管理
- 对比指标：入场价格偏离度、成交率、等待时间、最终P&L

#### P1: 订单管理优化

**目标**：在核心概念验证有效后，优化订单管理。

- 动态价格调整（ADJUST）：预测漂移时调整挂单价格
- 多级挂单：根据预测区间生成多个价位的订单（类似现有tranche机制）
- 成交概率实时更新：每根bar用新prediction重新估算未成交订单的成交概率
- 超时策略优化：根据市场状态（波动率高低）动态调整超时阈值

#### P2: 可进化参数

**目标**：将定价参数放入DNA，支持进化优化。

- `pricing_alpha_base`、`pricing_alpha_range`、`pricing_min_fill_prob` 作为可进化基因
- 进化引擎在参数空间中搜索最优入场价格策略

| 指标 | 计算方法 | 期望 |
|------|---------|------|
| 入场价格偏离度 | \|entry_price - signal_bar_close\| / sigma | B < A（挂单价格更好） |
| 成交率 | filled_orders / total_orders | > 60%（太低说明价格太激进） |
| 等待时间 | bars from creation to fill | 中位数 <= 3 bar |
| 价格改善 | signal_bar_close - entry_price（做多） | 正值，系统性的 |
| P&L对比 | 实验组 vs 对照组 | 实验组 >= 对照组 |

## 7. 风险分析

### 7.1 确定性风险

| 风险 | 影响 | 缓解 |
|------|------|------|
| 挂单等待期间市场大幅波动 | 在不好的价位被迫入场 | 超时保护 + 逆向选择保护（不挂太远） |
| 预测准确性不足导致挂单价不合理 | 成交率过低或价格无改善 | min_fill_prob 阈值 + 回退市价机制 |
| 改造影响现有回测/进化系统 | 进化结果不一致 | 通过配置开关（use_limit_orders=True/False）保持兼容 |

### 7.2 不确定性

| 不确定性 | 如何消除 |
|---------|---------|
| alpha_factor 的最优参数范围 | P0 阶段用实验数据校准，P2 阶段交给进化 |
| 15m bar内挂单成交判断的准确性 | 用 bar_high/low 判断触及，与真实行为足够接近 |
| 订单管理和现有tranche机制的兼容 | P0 阶段先只改入场，保留tranche用于加仓；P1 统一 |

## 8. 与现有系统的兼容性

### 8.1 配置开关

```python
@dataclass
class JudgmentConfig:
    # ... 现有字段 ...

    # 预测性订单管理配置
    use_limit_orders: bool = False        # False=市价执行(现有), True=限价挂单(新)
    pricing_alpha_base: float = 0.3       # 挂单激进程度基础值
    pricing_alpha_range: float = 0.5      # 置信度调节范围
    pricing_min_fill_prob: float = 0.3    # 最低成交概率
    order_max_wait_bars: int = 5          # 挂单最大等待bar数
```

`use_limit_orders=False` 时，系统完全保持现有行为，确保向后兼容。

### 8.2 进化系统兼容

- 进化回测时使用 `use_limit_orders=False`（现有行为），避免影响适应度评估
- 也可以用 `use_limit_orders=True` 进行实验性进化，对比适应度差异
- DNA中不强制包含pricing参数，进化系统通过JudgmentConfig传入
