# 模拟交易 (trading)

## 职责与边界
**负责**：
- 定义交易类型系统：Decision、AccountState、BarSignals、JudgmentConfig、Order、OrderEvent、PipelineResult
- 纯判断规则引擎：基于信号和账户状态生成交易决策（judgment.py）
- 订单生成器：信号 + 预测 → 限价/市价订单（order_generator.py）
- 订单生命周期管理器：成交检查、有效性验证、超时过期（order_manager.py）
- 决策管线：观察→预测→订单管理→SL/TP→执行→信号评估的完整 K 线处理（pipeline.py）
- 历史回放驱动器：用 DecisionPipeline 对历史数据快速验证（replay.py）
- 虚拟账户管理：K 线开盘价执行、止损止盈、杠杆、资金费率、滑点（account.py）
- 后台运行器：守护线程执行模拟交易任务，含崩溃恢复（runner.py）

**不负责**：
- 策略信号计算（由 strategy/executor 承担）
- 历史数据获取（由 data/updater 承担）
- 回测引擎（由 backtest/engine 承担，回测使用 vectorbt）
- 价格预测模型（由 prediction/ 承担）

**边界**：接收策略 DNA、市场数据和可选的预测器，输出模拟交易执行记录和权益快照。DecisionPipeline 是模式无关的核心——replay 和 live 共享同一条管线，仅数据源不同。

## 设计意图
模拟交易系统采用三层架构：OrderGenerator（价格计算）→ OrderManager（生命周期）→ VirtualAccount（执行）。核心设计是"信号→判断→决策→执行"四层分离加上可选的预测性订单管理路径。

两种执行路径通过 `use_limit_orders` 配置切换：
- **Legacy 路径**（use_limit_orders=False）：信号 → evaluate → pending_decision → 下一 bar 开盘执行（市价）
- **限价单路径**（use_limit_orders=True）：信号 → generate_order（限价）→ OrderManager 管理（成交/取消/过期）→ fill_order

DecisionPipeline 从 runner.py 的内联逻辑中提取出来，成为独立可测试的决策管线。ReplayRunner 复用同一条管线对历史数据运行快速验证（秒级 vs 实时天级）。

SL/TP 修正：止损执行价从 bar_open 改为触发价（stop-market），止盈执行价为目标价（limit）。

## 状态机

模拟交易任务状态流转：
```
待运行(pending) -> 运行中(running) -> 暂停(paused) / 已停止(stopped) / 错误(error)
```

订单状态流转：
```
pending -> filled（bar 价格触及订单价格）
pending -> cancelled（信号反转或预测偏移）
pending -> expired（等待超过 max_wait_bars）
```

DecisionPipeline 每 K 线处理顺序：
```
1. observe: 用上一 bar 预测结果更新 GARCH 状态
2. predict: 预测下一 bar 价格区间
3. manage: 管理活跃订单（成交/取消/过期）
4. SL/TP: 止损止盈检查（触发价执行）
5. 爆仓检查
6. 执行 pending_decision（上一 bar 的延迟决策）
7. PositionPlan 分层处理
8. 信号评估 → generate_order 或 evaluate → 新 pending_decision
9. 资金费率 + 权益快照
```

判断规则优先级（evaluate）：
```
Rule 0: max_hold_bars 安全阀（亏损持仓超时强制平仓）
Rule 1: exit/reduce 信号 + 有持仓 -> 检查最小持仓时间和最小盈亏比
Rule 4: entry 信号 + 反向持仓 -> 先平仓
Rule 2: entry 信号 + 无持仓 -> 开仓（initial_entry_pct 比例入场）
Rule 3: entry 信号 + 同向持仓 -> 加仓（仅盈利时）
Rule 5: 无信号 -> 持有
```
